# 访问速度与链路承载评估 · wang.xknot.si / xknot.si · 2026-10-25

这是一次端到端测量的记录，不是规范。方法在 `bench/README.md`，取数命令在本文末尾。
所有数字来自同一台压测机（开发机，darwin/arm64）在同一时段对公网入口的测量；换机器、
换时段、换数据量都不能直接比。

## 一句话结论

- **第一次打开**：未登录、空缓存、移动视口下 `load` 约 0.5 秒，LCP 约 0.6～0.7 秒，
  总传输 152KB（改造前 496KB，降 69%）。微信内置浏览器白屏已消除。
- **发帖**：120B 136ms、8KB 130ms、200KB 243ms（p50，含写库、审核入队、快照推送）。
- **读与刷新**：二级页 TTFB 55～60ms（入口缓存命中即直出）；发现页整屏 1.9MB、LCP 0.9 秒；
  单条卡片视图要等整条信息流，4.7MB，是当前最重的一屏。
- **Agent 与并发**：访客读 300 并发 553 RPS、p95 333ms；Agent 读 300 并发 387 RPS、
  p95 1148ms。300 并发下由描述符上限引起的 502 已经消除，剩下的 429 是按人配的检索配额。

## 测点与方法

链路有三段，混在一起看会得出互相矛盾的结论：

| 段 | 路径 | 由谁决定 |
| --- | --- | --- |
| 入口 | `/`、`/assets/*`、`/discover.json` | 入口 nginx 的缓存与磁盘快照、gzip、HTTP/2、证书 |
| 入口 → 实例 | `/api/*`，经反向 SSH 隧道 | 跨境链路、连接复用、隧道进程的 fd |
| 实例 | Backend + Postgres | Node、连接池、SQL |

- 人类首次打开：`bench/human/first-open.mjs`，Playwright 真浏览器，空缓存 / 空 localStorage，
  每轮一个新上下文；分 mobile / 4G 限速 / 微信 UA 三档。
- 人类读与刷新：`bench/human/visitor.mjs`，390×844 与 1280×800，每页取 3 轮中位数。
- 人类发帖：`bench/human/post.mjs`，WebUI 同源路径 `POST /api/web/intel`，三档正文。
- Agent 与并发：`bench/scripts/run.mjs` + `bench/k6/`，每档 30 秒、档间冷却 10 秒，
  访客读每 VU 一份 Cookie，Agent 读每 VU 一份授权码。
- 链路本身：`bench/scripts/link.mjs`，用来在把问题归给站点之前先看路。

**开跑前先看链路。** 2026-10-25 22:15 之后这条出口劣化到入口首页 TTFB 1.1～3.9 秒
（同样一页在 21:30 是 0.19 秒），此时任何 p95 量的都是链路排队。`run.mjs` 现在会在
入口首页 TTFB 超过 500ms 时先提示一句；本文的数字全部取自链路正常的那一小时。

链路正常时的分段（2026-10-25 21:06，`results/link-2026-10-25T13-06-19/`）：

| 指标 | p50 | p95 |
| --- | --- | --- |
| TCP 建连（含 DNS） | 62ms | 205ms |
| TLS 握手 | 63ms | 164ms |
| 冷请求 TTFB（`/`） | 188ms | 329ms |
| 热请求 TTFB（复用连接） | 56ms | 177ms |

下行 4 流 32.9Mbps（`/assets/*` 4.4MB / 1.13s），说明下行不是当前的限制，
标称的 20M 档位之上还有余量。上行这一轮没测（需要一个接受请求体的端点）；
隧道是单线程加密，上行更容易先满，要下结论需要另用 `iperf3` 或长时大文件交叉验证。

## 1. 人类新用户第一次打开

同一轮测量里三档并列，每档三轮：

| 档 | 挂载 | FCP | LCP | load | 请求 | 总传输 |
| --- | --- | --- | --- | --- | --- | --- |
| mobile 无限速 · 改造前 | 456ms | 260ms | 724ms | 514ms | 14 | 496KB |
| mobile 无限速 · 现在 | 260ms | 352ms | 708ms | 523ms | 9 | **152KB** |
| 4G 限速 · 改造前 | 578ms | 464ms | 1004ms | 674ms | 14 | 496KB |
| 4G 限速 · 现在 | 309ms | 528ms | 956ms | 692ms | 9 | **152KB** |
| 微信 UA · 改造前 | 451ms | 328ms | 724ms | 507ms | 14 | 496KB |
| 微信 UA · 现在 | 191ms | 256ms | 604ms | 471ms | 9 | **152KB** |

传输量从 496KB 降到 152KB，其中接口从 348KB（赞助图原件 PNG）降到 2KB。请求数从 14 降到 9。
LCP 在无限速档几乎没动，因为这一屏的 LCP 元素是首页那张 49KB 演示图，不是接口数据；
真正消失的是接口侧那 348KB。

微信白屏的修复不在这一批数字里，一并记在这里：`#app` 内联兜底 + 重试按钮、
`@vitejs/plugin-legacy` 产出 `nomodule` 回落包、构建目标降到 ES2015 并去掉
`String.prototype.replaceAll`、`index.html` 加 `Cache-Control: no-store`。

## 2. 人类发帖

`POST /api/web/intel`，每档 3 次；发布是 INSERT + 审核入队 + 快照推送触发：

| 正文 | 发布 p50 | p95 | 最大 |
| --- | --- | --- | --- |
| 120B | 136ms | 160ms | 160ms |
| 8KB | 130ms | 135ms | 135ms |
| 200KB | 243ms | 696ms | 696ms |

小/中两档基本等于「一次跨境往返 + 一次写库」，正文体积看不出差别；200KB 那一档的
p95 抬到 696ms，是请求体上传加上服务端 JSON 解析、正文落库的那一段。

## 3. 人类读与刷新

未登录、每页新一轮空缓存上下文，单位毫秒：

| 页面 | 视口 | TTFB | LCP | 传输 |
| --- | --- | --- | --- | --- |
| 首页 | mobile | 199 | 656 | 149KB |
| 首页 | desktop | 177 | 728 | 254KB |
| 发现页 | mobile | 56 | 888 | 1954KB |
| 发现页 | desktop | 94 | 576 | 1939KB |
| 卡片视图 | mobile | 56 | 184 | 4740KB |
| 星星 / 好友 / 通知 / 经济 | mobile | 54～58 | 70～372 | 1～4KB |

两级差别很清楚：二级页 TTFB 55～60ms，是入口缓存命中——`/assets/*` 按哈希名留 30 天、
页面骨架留 10 秒、`/discover.json` 落盘且 30 秒 stale-while-revalidate；
首页首屏 0.65 秒的 LCP 则由主包与演示图决定；
**发现页与卡片视图是重量所在**——60 条信息流、43 张带图，整屏 1.9MB；
从帖子链接直接进卡片（`/discover?post=<id>`）会把整条信息流一起渲染，122 个资源、4.7MB。
在 20M 线路上这是 0.8～1.9 秒的纯传输，在 4G 上要 4 秒以上。

已做的：卡片图统一走 `/display`（转过 EXIF、长边 1280 的 JPEG，入口缓存一天），
头像与卡片图 `loading="lazy" decoding="async"`。没做的：发现页仍是「一次把全部 60 条
塞进首屏」的取法，下一步应当是分页或按视口增量取，而不是继续压图片。

## 4. Agent 接口与并发承载

两轮完整结果，同一台压测机、同一时段、同一份数据（60 条 / 43 张图）。第二轮是带入口缓存的代码：

| 并发 | 场景 | RPS | 错误率 | p50 | p95 | p99 |
| --- | --- | --- | --- | --- | --- | --- |
| 150 | 访客读 | 291 | 0.00% | 144 | 301 | 353 |
| 200 | 访客读 | 377 | 0.00% | 150 | 320 | 526 |
| 300 | 访客读 | 553 | 1.17% | 172 | 333 | 566 |
| 150 | Agent 读 | 410 | 0.00% | 189 | 280 | 387 |
| 200 | Agent 读 | 373 | 0.05% | 312 | 597 | 759 |
| 300 | Agent 读 | 387 | 2.39% | 497 | 1148 | 1478 |

300 并发下各端点 p95：`/` 147、`/assets/*` 264、`/api/web/session` 291、`home` 314、
`discover.json` 350、`information` 368、`intel/:id` 404、`sponsors` 443、`search` 511；
Agent 侧 `profile` 869、`intel/:id` 851、`notifications` 933、`information` 1328、`search` 1632。

三个数字要分开读：

- **`/` 与 `/assets/*` 那两行是入口的能力**（147ms 已含一次跨境往返），和实例无关。
- **`/api/*` 的 p95 是「一次往返 + 排队」**：150 并发时 p50 189ms 基本就是一个 RTT，
  300 并发时 p50 抬到 497ms，说明入口到实例这一段开始排队，而不是库慢。
- **`search` 的 429 是配额，不是故障**：同一身份每分钟 120 次检索，300 并发里限流率
  12～15%，已经单列，不进错误率。要测真实容量，得让每个 VU 有独立身份，或在该实例上调配额。

### 300 并发的那 1～2% 502 找到了

入口错误日志里是 `recv() failed (104: Connection reset by peer) while reading response
header from upstream`，而实例侧健康。再往上翻隧道进程自己的日志：

```
socket: Too many open files
connect to 127.0.0.1 port 8080 failed: Too many open files
```

launchd 给常驻任务的软限是 256 个 fd，而一条转发连接占一个。并发过两百，隧道先撑不住，
把新连接直接 reset，入口记成 502——看起来像后端故障，实际是描述符上限。

修复是系统层的：新增 `ops/scripts/lib/fd-limit.sh`，只抬软限（`ulimit -Sn`，不动硬限）
到 8192，按硬限收敛、失败不拦启动；Backend 与隧道的 `exec` 之前各调用一次。
验证方式不依赖跨境链路：在入口主机上直接对回源端口并发建连，
300 条与 600 条都 100% 返回 200，隧道日志不再新增一行 `Too many open files`。

## 5. 这一批改了什么

| 改动 | 位置 | 针对的问题 |
| --- | --- | --- |
| 卡片图统一走 `/display` 并懒加载 | `backend/src/information.js`、`backend/src/sponsors.js`、`web/src/**` | 首屏把赞助图原件（348KB）和整张原图送进信息流 |
| 入口缓存页面骨架 10 秒；`/api/*` 不缓存 | `xknot.si/server/provision.mjs` 渲染的入口 vhost | 十秒内的重复导航不必再穿一次隧道；带会话的接口始终回源 |
| 接口缓存头分公开/私有 | `backend/src/routes/web.js` | 匿名响应给短缓存，登录态与只有当事人能读的媒体一律 `private` / `no-store`，不进共享缓存 |
| 微信兜底与旧内核回落包 | `web/index.html`、`web/vite.config.js`、`web/src/api.js` | 微信内置浏览器白屏 |
| 首帧守卫、legacy 语法下限、构建期解析检查 | `web/src/boot.js`、`web/vite.config.js`、`web/scripts/check-legacy.mjs` | 上一行没盖住的那一半，见第 7 节 |
| 入口按哈希名缓存 `/assets/`（30 天） | `xknot.si/server/provision.mjs` 渲染的入口 vhost | 发布删掉旧 HTML 引用的 chunk，缓存里的页面再也取不到自己那一版 |
| fd 软限抬到 8192 | `ops/scripts/lib/fd-limit.sh` 等 | 300 并发下隧道 `Too many open files` 导致的 502 |
| 快照取回带 8 秒超时 | `xknot.si/ops/snapshots.mjs` | 链路卡住时取回一直等，入口连续发旧快照 |
| 压测前提示链路已拥塞 | `bench/scripts/run.mjs` | 把链路排队误读成站点容量 |

## 6. 天花板在哪

按上面的数字，这套拓扑现在的容量是：

- **静态与访客读**：300 并发、553 RPS，p95 333ms。限制在入口 nginx 与这条 20M 出口，
  不在实例。
- **Agent 读**：150 并发内 p95 < 300ms；300 并发 p95 1.1s。限制在「入口 → 实例」这一条
  隧道：单条 SSH 连接复用所有转发，每个新连接多一次往返，300 并发时排队开始主导。
- **写**：200KB 正文 243ms，远没到瓶颈。

要继续往上，需要的是结构改动，不是调参：

1. 隧道从「一条 SSH 连接」变成「多条连接 + 入口侧负载分担」，或者干脆换成直连
   HTTPS 回源（有公网 IP 的实例就不需要隧道）。
2. Agent 读路径上的「看过」记录目前是请求内写入；并发上来后它是读延迟的一部分，
   应当改成批量或异步落库。
3. 发现页从「一次取 60 条」改成按页/按视口增量取。

## 7. 补充：白屏的第二层成因（2026-10-26）

第 5 节那三层（内联首帧、`nomodule` 回落包、`no-store`）只覆盖「脚本没跑起来」。
微信里仍然是空白，说明脚本跑到了，然后崩在别处：

- **`app.mount()` 会先清空 `#app`，而兜底就写在里面。** 首屏渲染抛一次错，屏幕上唯一
  的内容和重试按钮一起被抹掉；12 秒计时器找 `[data-knot-boot]` 也找不到，什么都不做。
  现在 `web/src/boot.js` 在挂载前留快照，首帧完成前的错误（`errorHandler`、
  `window.error`、`unhandledrejection`）把兜底放回去，并写出错误类型请用户截图。
- **legacy 包按 `chrome >= 61` 转译，`async` 与对象展开原样留在包里。** 不支持
  `type="module"` 的 WebView 只会执行这一份，拿到的是语法错误——两套产物同时失效。
  下限降到 `chrome >= 53`，并把「按各自声称的语法级别解析全部产物」挂进
  `npm run build:web`：下限再被调高，失败在构建，而不是在用户手机上。
- **计时器判定改用标记。** 挂载成功在 `<html>` 上打 `data-knot-ready`，计时器只认它，
  不再按 `.app-shell` 之类的视图 class 猜——首页、登录门、信息流的根节点各不相同。

验证（真 Chromium，可打本地 dist 也可打线上）：

```bash
cd bench
npm run boot -- --base https://wang.xknot.si   # 8 项：兜底恢复、接口全挂不白屏、计时器不误判
```

### 结论（2026-10-26 10:43 现场确认）

微信内置浏览器里 `https://wang.xknot.si/` 与 `https://wang.xknot.si/?v=2` 都能正常
打开，带不带参数返回的 HTML 一模一样（同一份 `sha256` 前缀、同一个 etag）。所以这次
不是缓存绕过的功劳，是构建真的修好了。

主因是 legacy 包里的 `async`：旧包的 `index-legacy-*.js` 在解析到
`D: async function(e){…}` 时就抛错，而那是不支持 `type="module"` 的内核**唯一**会
执行的脚本——现代包它不下载，legacy 包它解析不了，两套同时失效。下限压到
`chrome >= 53` 之后，legacy 包的语法要求回到 ES2015（箭头函数、`const`、解构），
X5 与 WKWebView 都能解析。

这一层定住了边界：**ES2015 是 legacy 包的语法底线，不是 ES5**。2016 年以前的内核
（Android 5 / Chrome 44 及更早、iOS 9）仍会失败，那时看到的是内联兜底那句
「页面还没有加载出来。」加「用浏览器打开」的指引，不会再是一片白。要真降到 ES5
需要换转译档位，包体积会明显变大，当前没有这个需求。

### 同一天补的第三层：旧页面还能取到自己那一版 chunk

上面两层都是「让新页面能跑」。这一层是「让旧页面还能跑」：新包一发布，上一版的
chunk 就不再出现在入口磁盘上，而还攥着旧 `index.html` 的地方（X5 离线缓存、没关的
标签页、中间代理）随后请求的正是那些文件名。

入口磁盘上只留占位页、ACME 校验文件、robots/sitemap 与公开快照；`/assets/` 不落盘，
按哈希名由 nginx 缓存 30 天（见
[`xknot.si/server/provision.mjs`](../../xknot.si/server/provision.mjs) 渲染的 vhost）：
chunk 名带内容哈希，文件内容一变名字就变，所以旧名字命中的那份缓存始终对应旧内容；
缓存满了按容量淘汰，不按发布时间删。
